Sleepless Welford

How to keep an average (and a "how scattered are the numbers?" score) up to date while new data keeps arriving, without ever re-reading the old data.

Homework 4 · Statistics 2026

The idea in 30 seconds.
You have seen apps that say "4.3 stars from 120 reviews". When review number 121 arrives, the app does not re-read all 120 old reviews. It only needs two things: the current average and how many reviews there are. It nudges the average a little toward the new review, and it is done.

That trick is old and simple. Welford's trick does the same for the second question we usually care about: how spread out are the reviews? (all 5 stars? or a mix of 1s and 5s?) It keeps just three numbers, updates them in three lines of code, and never needs the old data again. That is why I call it "sleepless": it is always up to date, and it never needs to go back and redo anything.
Mini dictionary (open it if a word is new to you)
Mean
The normal average: add everything up and divide by how many values there are.
Variance
A number that says how scattered the values are around their average. Small = everyone is close to the average. Big = values are all over the place.
SS ("sum of squares")
Take each value's distance from the average, square it (so negatives don't cancel positives), and add them all. Variance is just this total, divided by (how many values − 1).
Sample
The few values you actually got to see, as opposed to "everything that could ever happen".
Estimate
A guess about the real world made from a sample.

Exercise 1 - Welford's trick

Part A: updating the average (Knuth's version)

Suppose after 3 exam grades the class average is 4, and a 4th grade of 8 arrives. The new grade is 4 points above the old average, and it is one of 4 grades now, so it pulls the average up by 1/4 of that gap:

new average = old average + (new value - old average) / k example: 4 + (8 - 4) / 4 = 5

In words: move the average toward the new value by a share of 1/k of the gap. The more values you already have, the less a new one can move the average. That is exactly how you would expect it to behave.

Part B: updating the spread (Welford's contribution)

Spread is measured by SS (the total of the squared distances from the average). The surprise is that it also has a tiny update rule:

new SS = old SS + (gap before the update) x (gap after the update) gap before = new value - old average gap after = new value - new average

Why does it work? The short version: when a new value arrives the average itself moves, which changes every old distance a little. Careful bookkeeping shows all those small changes add up to exactly the product above. If you want to see that bookkeeping, it is in the box below. If not, just trust it and look at the example after it, then try the calculator.

Show me the math (optional)

Call Mk the average of the first k values and d = xk - Mk-1 the "gap before". From Part A: Mk - Mk-1 = d/k.

We want SSk = Σ (xi - Mk)². Rewrite every distance using the old average:

x_i - M_k = (x_i - M_(k-1)) - d/k

Old values (i ≤ k-1). When we square and add, the middle term contains Σ(xi - Mk-1), which is zero (distances to an average always cancel out). What remains:

SS_(k-1) + (k-1) * d^2 / k^2

The new value (i = k). Its distance to the new average is d - d/k = d(k-1)/k, so its square is:

d^2 * (k-1)^2 / k^2

Add both parts:

SS_k = SS_(k-1) + (k-1) * d^2 / k

And since the "gap after" is xk - Mk = d(k-1)/k, we get d · (xk - Mk) = (k-1)d²/k, which is the same thing:

SS_k = SS_(k-1) + (x_k - M_(k-1)) * (x_k - M_k)

Both gaps point in the same direction, so SS never goes down. Good: spread can only grow when you add data.

Part C: from SS to variance

variance = SS / (k - 1) (needs at least 2 values)

Why k-1 and not k? We measure distances from the sample's own average, and that average always sits "in the middle of" the data we have, so the distances come out a little too small. Dividing by one less than the count fixes that exactly (the experiment below shows it working). Dividing by k would make the guess too low on average.

The same thing can be written to update the variance directly: new variance = ((k-2) × old variance + gap before × gap after) / (k-1).

A tiny worked example

Values arrive one by one: 2, 4, 9.

stepnew valuegap beforeaverage aftergap afterSS
122 − 0 = 2200 + 2×0 = 0
244 − 2 = 2310 + 2×1 = 2
399 − 3 = 6542 + 6×4 = 26

Final answer: average = 5, variance = 26 / (3 − 1) = 13. Check the slow way: distances are 3, 1, 4, squares are 9 + 1 + 16 = 26. Same.

The code (three lines)

function push(s, x) {
  const d = x - s.mean;          // 1) how far is the new value from the current average?
  s.mean += d / ++s.k;           // 2) count it, then nudge the average toward it
  s.SS   += d * (x - s.mean);    // 3) update the spread: gap before x gap after
}
// start with s = {k:0, mean:0, SS:0}.  variance = s.SS / (s.k - 1)

Order matters: line 1 uses the old average, line 3 uses the new one (updated in line 2). Memory used: three numbers, no matter how much data goes through.

Exercise 2 - A crowd of hackers

The story. Imagine m hackers. Each one tries to break into n different systems, and every attempt gets a score from 0 to 10. So each hacker ends up with their own list of n scores.

Each hacker then does what a real scientist does: looks only at their own list and computes an average and a spread (using Welford). Nobody knows the "true" numbers behind the scores, so each hacker is making a guess. The big question: are these guesses any good? Since we are running a simulation, we do know the truth, so we can check.

Where the scores come from

I chose a simple rule: a system has 10 checks, and the hacker passes each check with probability 30%. The score is how many checks they passed (this is called a Binomial(10, 0.3) distribution). So scores are usually low (around 3), and high scores like 8 or 9 are rare.

What did we learn?

1. A hacker's guess is fair. Look at "average of all the hackers' averages": it lands very close to the true 3, and the average of the variances lands very close to the true 2.1, even when each hacker only tried 5 systems. Individual hackers can be off, but they are not off in a consistent direction: some guess too high, some too low, and it balances out. Statisticians call this unbiased. This is also why we divide by k−1 for the variance: dividing by k would make the guesses too small on average.
2. Why this matters in real life. In real life there is one hacker (one sample), and the true numbers are unknown. This experiment shows that using that one sample to guess the average and the spread is a sound move: the guess is not tilted in any direction. It is the same logic behind polls ("we asked 1000 people") and clinical trials. And thanks to Welford, the guess can be updated live as each new answer arrives.
3. More systems per hacker means more agreement. Compare the rows of the table: as n grows, the hackers' guesses become more similar to each other and closer to the truth, and the histograms get narrower. The rule of thumb: to cut the disagreement by 10 times you need 100 times more data (it shrinks like 1 over the square root of n). So the first few data points help a lot, and later ones help less and less.
4. The spread is harder to guess than the average. Compare the two columns: with the same n, the variance guesses differ more from each other (in relative terms) than the average guesses do. Guessing "how scattered things are" needs more data than guessing "where the middle is", because it depends on rare extreme values.
5. Two different knobs. n (systems per hacker) makes each hacker's guess better. m (number of hackers) does not improve any single hacker; it only makes our picture of "how guesses behave" clearer and smoother. Try changing each one and see.
